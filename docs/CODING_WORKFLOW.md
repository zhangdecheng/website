# FLOURISH CULTURE Coding Workflow

这份规范把项目复盘转成后续 coding 的默认工作方式。它解决的重点不是
“页面怎么写”，而是避免需求漂移、预览/源码/线上不一致，以及发布后无法
快速定位和回滚。

## 1. 开工前先冻结范围

每个改动开始前，先在任务或变更记录中写清楚以下内容；没有验收标准时不
进入实现阶段：

```text
目标：本次要改变什么
非目标：本次明确不改什么
验收基准：预览 URL、截图或具体文案/尺寸
影响面：静态页面、Contact API、Nginx、/review/、资产或文档
发布对象：只发静态包，还是同时发服务/Nginx
回滚点：上一个可用 tag、备份或服务器 release
```

视觉修改、功能修改和生产运维修改分三段验收：

1. 视觉段：先确认布局、图片、Logo、文案和响应式效果。
2. 功能段：再验证表单、API、错误处理、权限和安全边界。
3. 生产段：最后验证构建包、服务、Nginx、公开域名和 `/review/`。

小改动如果只影响视觉，也不要在同一轮顺手扩大到后端、DNS 或 Review
服务；新增范围必须重新记录并重新验收。

## 2. 单一源码与构建产物规则

- `index.html`、`styles.css`、脚本和 `assets/` 是源码真相；`review-editable.html`
  只用于本地试改，不能直接发布。
- 生产包必须由 `npm run build:artifacts` 生成；禁止手工从 `dist/` 另行压缩
  或从旧 `release/` 目录拼包。
- 构建脚本只能复制和整理文件，不能悄悄改写源码字节、图片路径或文案。
  任何路径改写都必须有测试证明“预览页面 = 构建页面”。
- 资产替换必须同时更新资产文件、引用、尺寸/裁切规则、资产清单和测试。
  Logo 默认使用透明背景；若供应商图片带底色，先处理资源再进入页面布局。
- Logo 轨道新增或删除品牌时，必须保持两个循环内容、顺序、无障碍属性和
  CSS 光学尺寸同步，并更新测试。后续重构时应优先改成“单一品牌列表生成
  首轮 + 无障碍复制轮”，不再新增手工重复 HTML 或依赖未说明的 `nth-child`
  序号。

## 3. 发布候选物生命周期

发布对象必须能回答“哪份源码、哪次构建、哪个线上版本”：

```text
draft -> local accepted -> commit/tag archive -> deploy -> public read-back
```

- `local accepted` 前不得发布；至少要有内容/契约测试、构建检查和浏览器
  响应式证据。
- `commit/tag archive` 必须发生在部署前，tag 名称要包含功能/视觉变更和日期。
  发布记录至少保存 commit/tag、静态包和 Contact 包 SHA-256、目标主机、
  备份路径和回滚目标。
- 线上发布只接受已归档候选物；线上读回的首页、CSS、关键 Logo/图片和 API
  健康结果必须与候选物核对。
- 线上失败时先停止扩大变更，保留失败证据，按 runbook 回滚到上一个 tag 或
  release；不要用“重新复制一次”掩盖版本来源问题。

## 4. 发布前唯一门禁

本地发布前运行：

```bash
npm run release:verify
```

它按固定顺序执行：

1. `git diff --check`，拦截明显的补丁/空白错误；
2. 构建静态和 Contact 生产包；
3. 运行静态、发布契约和 Contact 核心测试；
4. 使用 Chrome 在桌面、平板和两种移动宽度执行浏览器 QA。

这个命令只生成本地 `dist/`、`release/` 和 QA 证据，不执行 SSH、Cloud
Assistant、Git push 或生产部署。Chrome 不可用时必须明确记录为“未完成”，
不能把 Node 测试通过当作视觉验收通过。

## 5. 证据和阻塞项

所有交接记录使用三种标签：

- **已确认**：有文件、命令输出、实际 HTTP/浏览器读回或服务器回读支持；
- **合理推断**：由已确认事实推导，但没有直接读回；
- **未确认**：缺权限、缺账号、缺收件箱访问或未完成真实环境验证。

静态页面发布成功，不等于 Contact 邮件进入收件箱，也不等于 GitHub 源码
已同步，更不等于 `/review/` 内容回归已完成。这些都必须作为独立 gate 记录，
不能用一个“发布成功”覆盖。

## 6. 完成定义

一次 coding 变更只有同时满足以下条件，才可以汇报为完成：

- 范围和非目标明确，验收页面或截图已确认；
- 源码、构建产物和引用资产一致；
- 对应测试和 `npm run release:verify` 通过，或明确记录失败原因；
- 变更已 commit/tag 归档（若进入生产发布）；
- 相关 README、CHANGELOG、交接/发布记录已更新；
- 线上变更有公开读回、备份和回滚证据；
- 未确认的收件箱、远程仓库、Pages 或 Review 事项单独列出。

## 7. 本项目下一步优化顺序

按收益排序，后续不要再重复投入在同一类返工上：

1. 先持续使用本门禁，消除预览、源码和发布包漂移；
2. 将 Logo 轨道重构为单一品牌数据源，自动生成首轮和复制轮；
3. 将静态包、Contact 包和部署元数据绑定为一个带版本号的候选物；
4. 稳定唯一的制品传输通道，再考虑自动化发布；
5. 把邮箱收件箱、远程 Git、Pages 和 Review 内容回归分别接入对应验收，
   不再把它们混在页面视觉修改中。
